# Техническое задание (ТЗ): участники, доступ и переписка в сделках

## 1. Цель

Доработать сделки партнерского портала так, чтобы ответственный менеджер вендора мог передавать сделку другому менеджеру, дистрибьютор подключался только после явной отправки сделки, сотрудники партнера и дистрибьютора могли подключать коллег своей компании, а переписка была разделена на изолированные каналы.

## 2. Термины

- **Вендор** — Trinity.
- **Партнер** — компания-интегратор, зарегистрировавшая сделку или участвующая в ней.
- **Дистрибьютор** — компания-дистрибьютор, выбранная менеджером вендора.
- **Ответственный менеджер** — единственный текущий менеджер вендора, ведущий сделку.
- **Участник сделки** — конкретный пользователь, подключенный к сделке от своей компании.
- **Канал** — изолированная переписка с фиксированным составом сторон.

## 3. Общие правила доступа

1. Все ограничения проверяются на backend для списка, статистики, прямого открытия сделки, участников, сообщений, вложений и уведомлений.
2. Пользователь видит сделку только при наличии права и участия в ней. Для дистрибьютора дополнительно требуется явная отправка ему сделки.
3. Обычный сотрудник вендора после передачи сделки другому менеджеру теряет доступ. Исключение допускается только по отдельному административному праву аудита или переназначения.
4. Изменения ответственного менеджера, дистрибьютора и участников записываются в журнал действий.

## 4. Передача сделки менеджеру вендора

1. Текущему ответственному менеджеру и пользователю с административным правом доступна команда **«Передать сделку»**.
2. Выбрать можно только активного сотрудника вендора с правом ведения сделок.
3. После подтверждения новый пользователь становится единственным ответственным менеджером, получает доступ и уведомление; предыдущий менеджер теряет доступ.
4. Остальные участники, сообщения, файлы и конфигурации сохраняются.
5. Операция атомарна и журналируется: сделка, старый и новый менеджеры, инициатор, время, необязательная причина.

## 5. Каналы переписки

В сделке предусмотрены четыре типа каналов:

| Канал | Видимость |
|---|---|
| Вендор — дистрибьютор | Ответственный менеджер вендора и участники дистрибьютора |
| Вендор — партнер | Ответственный менеджер вендора и участники партнера |
| Партнер — дистрибьютор | Участники партнера и дистрибьютора |
| Общий | Все текущие участники сделки |

Требования:

1. Недоступные каналы, сообщения, авторы, счетчики непрочитанного, вложения и уведомления не выдаются API.
2. Сообщение хранит канал, автора, компанию автора на момент отправки, текст, даты создания/изменения/удаления и вложения.
3. Для каждого пользователя хранится состояние прочтения каждого доступного канала.
4. Новый сотрудник компании получает историю разрешенных этой компании каналов; удаленный участник сразу теряет доступ.
5. Новый менеджер вендора после передачи получает историю каналов вендора.
6. Канал привязывается к конкретным компаниям. При смене дистрибьютора новый дистрибьютор не получает закрытую переписку предыдущего; создаются новые каналы.
7. Доступ к файлу сообщения проверяется через доступ к каналу, а не только по URL.

## 6. Необязательный дистрибьютор

1. При создании и регистрации сделки поле **«Дистрибьютор»** необязательно.
2. Без дистрибьютора доступны регистрация сделки, назначение менеджера вендора, работа партнера с вендором, участниками, конфигурациями и спецификациями.
3. После регистрации менеджер вендора выбирает действующую компанию-дистрибьютора.
4. Выбор компании не предоставляет ей доступ автоматически.
5. Состояния: **«Дистрибьютор не выбран»**, **«Выбран, не отправлено»**, **«Отправлено»**, **«Доступ отозван»**.

## 7. Отправка дистрибьютору

1. После выбора компании менеджеру вендора доступна команда **«Отправить дистрибьютору»**.
2. До отправки сотрудники дистрибьютора не видят сделку, не открывают ее по прямой ссылке и не получают сообщения или уведомления.
3. После отправки фиксируются инициатор и время, дистрибьютор получает доступ, создаются его каналы и отправляются уведомления.
4. Повторный запрос идемпотентен и не дублирует участников, каналы или уведомления.
5. При смене дистрибьютора отправка сбрасывается; новый дистрибьютор подключается только отдельным нажатием кнопки.
6. Менеджер вендора или пользователь с отдельным правом может отозвать доступ. История сохраняется для аудита.

## 8. Участники своей компании

1. Партнер и подключенный дистрибьютор могут добавлять только активных сотрудников своей компании.
2. Нельзя добавить сотрудника другой компании, удаленного пользователя, повторного участника или сотрудника дистрибьютора до отправки сделки.
3. Добавленный сотрудник получает карточку сделки, разрешенные его ролью действия, каналы своей компании и уведомление.
4. Добавление в сделку не расширяет ролевые разрешения пользователя.
5. После удаления доступ прекращается немедленно, а сообщения и журнал действий сохраняются.

## 9. Матрица видимости

| Объект | Менеджер вендора | Партнер | Дистрибьютор до отправки | Дистрибьютор после отправки |
|---|---:|---:|---:|---:|
| Карточка сделки | Да | Да | Нет | Да |
| Конфигурации | Да | По роли | Нет | По роли |
| Общий канал | Да | Да | Нет | Да |
| Вендор — партнер | Да | Да | Нет | Нет |
| Вендор — дистрибьютор | Да | Нет | Нет | Да |
| Партнер — дистрибьютор | Нет | Да | Нет | Да |
| Выбор и отправка дистрибьютору | Да | Нет | Нет | Нет |
| Добавление сотрудника своей компании | По праву | Да | Нет | Да |

## 10. Модель данных

Нужны нормализованные таблицы:

- `deal_participants`: сделка, пользователь, компания, сторона (`vendor`, `partner`, `distributor`), роль, кто и когда добавил/удалил, активность;
- `deal_channels`: сделка, тип канала, первая и вторая компании, даты создания и архивирования;
- `deal_messages`: канал, автор, компания автора, текст, даты создания/изменения/удаления;
- `deal_message_attachments`: сообщение, файл, тип, размер, автор и дата загрузки;
- `deal_channel_reads`: канал, пользователь, последнее прочитанное сообщение/время;
- `deal_manager_transfers`: сделка, старый и новый менеджеры, инициатор, причина и время.

В сделке дополнительно хранятся даты и инициаторы отправки дистрибьютору и отзыва доступа. Наличие `distributor_company_id` само по себе не означает доступ.

## 11. Интерфейс

В карточке сделки добавить:

- блок участников с группировкой по компаниям;
- ответственного менеджера и действие передачи;
- выбор дистрибьютора, статус доступа, действия отправки и отзыва;
- добавление и удаление сотрудника своей компании;
- переписку со вкладками доступных каналов и счетчиками непрочитанных сообщений;
- системную историю изменений.

## 12. Миграция существующих данных

1. `responsible_manager_id` становится текущим ответственным менеджером.
2. Создатель сделки добавляется участником партнера.
3. Существующие комментарии переносятся в общий канал после отдельной проверки миграционной выборки.
4. Существующие дистрибьюторы не должны получить новый доступ только из-за заполненного `distributor_company_id`; фактически существовавший доступ сохраняется по согласованному правилу миграции.
5. Миграция не удаляет историю и формирует проверяемый результат.

## 13. Приёмка

Обязательно проверить передачу сделки, регистрацию без дистрибьютора, выбор без открытия доступа, отправку и повторную отправку, отзыв и смену дистрибьютора, отсутствие доступа к старым каналам, добавление/удаление коллеги, все четыре канала под тремя сторонами, прямые запросы к чужим сообщениям и файлам, статистику, уведомления и мобильный интерфейс.

Готовность требует TypeORM-миграций, автоматических тестов матрицы доступа, сборки backend и frontend, локального применения миграций, перезапуска backend, проверки логов и HTTP smoke-теста.
